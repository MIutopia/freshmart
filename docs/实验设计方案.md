# 实验设计方案

> 适用课题：生鲜电商称重结算中**金额与库存双维度一致性**的保障机制设计与验证
> 对应系统：FreshMart 多商家生鲜电商（后端 7,577 行 Java、47 个 Flyway 迁移、96 个 REST 端点）
> 本文档定位：论文第三章（方法）与第四章（实验）的初稿框架，所有实验均可基于现有代码直接实现。

---

## 1. 研究问题与假设

### 1.1 研究问题

生鲜商品按重量计价，下单时只能给出**预估克数**，实际交付重量须在分拣称重后才能确定。这导致两个维度必须同时保持正确：

- **金额维度**：预估金额与实收金额的差额如何归属（退回用户 / 平台承担 / 转人工）；
- **库存维度**：实际出库克数与预占克数的差额如何回补到具体批次。

现有做法通常只处理金额差额，忽略克数回补，导致批次账实长期偏离。本课题围绕这一缺口提出三个研究问题：

| 编号 | 研究问题 |
| --- | --- |
| **RQ1** | 在「预占 → 支付核销 → 称重调整 → 退款回补」的完整生命周期中，如何定义并保证金额与库存的双维度一致性？ |
| **RQ2** | 称重差额按**整单分摊**与按**订单项逐项回补**，两种粒度在克数误差与批次偏差上的差异有多大？ |
| **RQ3** | 在重复提交与并发操作的条件下，全链路幂等设计与悲观锁机制是否足以避免重复入账与负库存？ |

### 1.2 研究假设

| 编号 | 假设 | 证伪条件 |
| --- | --- | --- |
| **H1** | 所设计的三阶段机制（预占、核销、回补）可在任意合法操作序列下保持全部不变式成立 | 出现任一不变式违反 |
| **H2** | 逐项回补的克数误差为零，而整单分摊在「订单项跨多批次且偏差方向相反」时会产生可测量的批次级偏差 | 两种粒度误差无显著差异 |
| **H3** | 幂等键配合唯一约束可使重复与并发请求的有效变更次数恒为 1 | 出现有效变更次数大于 1 |

## 2. 系统建模

### 2.1 一致性不变式

不变式是后续所有实验的判定依据。定义如下符号：

- `avail(b)`、`resv(b)`：批次 `b` 的可用克数与已预占克数；
- `in(b)`：批次 `b` 累计入库净重；
- `shipped(b)`：批次 `b` 累计实际出库克数（以订单项实际称重为准，未称重时取预占克数）；
- `restocked(b)`：批次 `b` 累计退货回补克数；
- `Δ(b)`：批次 `b` 的累计称重回补量（正数补扣、负数退回）。

```text
I1（非负性）    ∀b:  avail(b) ≥ 0  ∧  resv(b) ≥ 0
I2（预占约束）  ∀b:  resv(b) ≤ avail(b)
I3（批次守恒）  ∀b:  avail(b) + resv(b) + shipped(b) − restocked(b) + Δ(b) = in(b)
I4（订单项守恒）∀o:  Σ_items actual_grams = weighing_adjustments.actual_grams
I5（金额守恒）  ∀o:  refund_amount + absorbed_amount = max(actual − prepaid, 0)
                    且当 actual < prepaid 时  refund_amount = prepaid − actual
I6（粒度一致性）∀o:  Σ_items inventory_adjust_grams = inventory_adjust_grams(整单记录)
I7（分摊无损）  ∀o:  Σ_batches share(b) = actual_grams − prepaid_grams
```

> **I7 说明**：这是实现中最易出错的一条。分摊采用「按预占比例计算、最后一批兜底剩余」的策略，若不做兜底处理，逐批四舍五入会产生累计误差，使回补总量不等于应有差额。实验 E2 将专门量化这一误差。

### 2.2 关键状态机

**子订单状态**（决定称重入口的合法性）：

```text
PENDING_PAYMENT ──支付成功──▶ WAITING_PICKING ──拣货──▶ PICKED ──送达──▶ DELIVERED
        │                                                    │
        └──超时/取消──▶ CANCELLED                             └──退款完成──▶ REFUNDED
```

**称重调整只允许在 `WAITING_PICKING`、`PICKED`、`DELIVERED` 三个状态下提交**，且每个子订单最多一条记录（由 `uk_weighing_order` 唯一键约束）。

**库存预占状态**：

```text
ACTIVE ──支付成功（核销）──▶ 已扣减 avail 与 resv
   │
   └──超时未支付（释放）──▶ RELEASED（仅扣减 resv）
```

### 2.3 并发控制机制（实验考察对象）

实现采用两种互补手段，二者均需在实验中检验：

| 手段 | 位置 | 作用 |
| --- | --- | --- |
| **悲观行锁** `SELECT ... FOR UPDATE` | 13 处，含支付单、退款单、结算单、预占记录、对账差异 | 串行化同一实体的并发修改 |
| **条件更新（CAS 语义）** | 批次扣减 `WHERE available_grams >= ?` | 库存不足时更新影响行数为 0，触发回滚 |
| **唯一约束** | `uk_weighing_order`、各表 `idempotency_key` | 从数据库层拦截重复写入 |

## 3. 实验设计

### E1 不变式随机回归

**目的**：验证 H1，检查任意合法操作序列下 I1–I7 是否恒成立。

**方法**：构建**操作序列生成器**，从以下原子操作中随机采样并施加于同一组订单与批次：

| 原子操作 | 说明 |
| --- | --- |
| `reserve` | 下单预占批次克数 |
| `pay` | 支付成功，核销预占 |
| `expire` | 预占超时，由任务释放 |
| `weighItem` | 逐项称重，回补差额 |
| `weighWhole` | 整单称重，按订单分摊 |
| `refund` | 售后审核通过，触发退款 |
| `completeManualRefund` | 完成人工退款并生成库存处置 |
| `disposition` | 处置为回库（RESTOCKED）或报损（DISCARDED） |
| `receive` | 称收入库，累加批次可用克数 |

**变量**：序列长度（20 / 50 / 100）× 随机种子（30 个）

**样本量**：3 × 30 = 90 条序列，合计约 6,300 次原子操作

**度量**：每条序列结束后逐条校验 I1–I7，记录违反次数与违反时的状态快照

**判定标准**：**违反次数必须为 0**。任一违反即为机制缺陷，需定位并修复后重跑。

**实现要点**：

```java
// 每个原子操作后校验，便于定位首个违反点
assertInvariants(orderId);
// 非法前置条件应被拒绝而非静默忽略
// 例如对未送达订单申请退款应抛 409
```

---

### E2 分摊粒度对照实验（核心实验）

**目的**：验证 H2，量化整单分摊与逐项回补的克数误差差异。

**方法**：控制以下四个因子，构造订单并施加称重，比较两种粒度下的实际回补量与理论应有差额。

| 因子 | 水平 | 说明 |
| --- | --- | --- |
| 分摊粒度 | 整单 / 逐项 | 自变量 |
| 订单项数 | 2 / 5 / 10 | 影响分摊轮次 |
| 每项跨批次数 | 1 / 3 / 5 | 影响逐批取整次数 |
| 偏差方向 | 同向 / 反向 | 反向指部分项变重、部分项变轻 |

**样本量**：2 × 3 × 3 × 2 = 36 个组合，每组合重复 30 次（随机克数与批次分配）= **1,080 次实验**

**度量指标**：

```text
总量误差率   ε_total = |Σ 实际回补 − 应有差额| / 应有差额
批次级误差   ε_batch(b) = |Δ(b) − share_expected(b)|
误差发生次数 N_err = count(组合中 ε_total > 0)
```

**预期结果**：

- 逐项回补：`ε_total = 0` 恒成立（每个订单项的差额由其自身批次独立分摊，最后一批兜底）；
- 整单分摊：在「偏差方向相反」且「跨多批次」的组合下，`ε_total` 可能非零，且订单项数越多、跨批次数越多，误差累积越明显。

**判定标准**：若逐项回补的 `N_err > 0`，则 I7 存在实现缺陷；若两种粒度无差异，则 H2 被证伪。

**统计处理**：对 `ε_total` 做分组描述性统计（均值、标准差、最大值），并用箱线图呈现 36 个组合的分布差异。

### E3 幂等性实验

**目的**：验证 H3，检查重复与并发请求下的有效变更次数。

**方法**：三个子场景，每个场景重复 50 轮：

| 场景 | 操作 | 期望 |
| --- | --- | --- |
| E3-a 顺序重放 | 同一幂等键顺序提交 2 / 5 / 10 次 | 有效变更恰好 1 次，其余返回首次结果 |
| E3-b 并发同键 | 10 个线程用同一幂等键同时提交 | 恰好 1 个成功，其余返回首次结果或冲突 |
| E3-c 不同键同实体 | 同一子订单用不同幂等键提交称重 | 恰好 1 次成功，其余因唯一键返回冲突 |

**度量**：

```text
有效变更次数   应恒为 1（库存变动、金额入账、台账记录三者独立统计）
台账记录数     fee_ledgers 中该业务键的记录数应恒为 1
响应一致性     同键重放返回的业务对象应完全一致
```

**判定标准**：任一场景出现有效变更次数 > 1，即 H3 被证伪。

**实现要点**：并发场景使用 `ExecutorService` 配合 `CountDownLatch` 保证同时发起；断言需在事务提交后重新查询数据库，而非依赖返回值。

---

### E4 并发安全实验

**目的**：验证悲观锁与 CAS 更新在竞争条件下的有效性。

**场景设计**：

| 场景 | 并发操作 | 观察目标 |
| --- | --- | --- |
| E4-a | 8 线程同时对同一批次执行称重补扣 | 是否出现 `avail(b) < 0`；成功次数是否与库存余量匹配 |
| E4-b | 称重补扣 与 退款回补 并发作用于同一批次 | 是否出现丢失更新 |
| E4-c | 预占、支付核销、超时释放三者并发 | 是否出现重复核销或重复释放 |
| E4-d | 秒杀活动 20 线程并发下单（库存仅够 10 单） | 是否超卖；成功数是否恰为 10 |
| E4-e | 同一退款单并发审核 | 是否重复退款 |

**变量**：并发度（4 / 8 / 16 线程）

**样本量**：5 场景 × 3 并发度 × 20 轮 = **300 次**

**度量**：

```text
负库存次数            应为 0
库存超卖量            Σ成功预占 − 初始库存，应 ≤ 0
重复入账次数          fee_ledgers 同键记录数 − 1，应为 0
失败率                竞争失败（返回 409/400）的比例，作为参考指标而非缺陷
```

**判定标准**：负库存次数与重复入账次数均须为 0。**允许存在失败**——条件更新失败并回滚是设计的预期行为，应作为「正确拒绝」记录而非错误。

---

### E5 故障注入实验

**目的**：验证异常路径下的回滚完整性，即不出现部分提交。

**注入点**：

| 编号 | 注入方式 | 期望行为 |
| --- | --- | --- |
| E5-a | 使批次可用克数小于待补扣差额 | 整单回滚，`inventory_adjust_grams` 不落库 |
| E5-b | 删除中间批次 | 抛冲突并回滚，其余批次不被修改 |
| E5-c | 复用已存在的幂等键 | 返回首次结果，不产生第二次变更 |
| E5-d | 在批次扣减与调整记录写入之间抛异常 | 两侧同时回滚，无残留 |
| E5-e | 对未送达订单申请退款 | 返回冲突，不生成退款单 |

**度量**：注入后的**残留状态量** —— 数据库中各表记录数与注入前之差，除预期记录外应全为 0。

**判定标准**：残留状态量必须为 0。

## 4. 度量指标汇总

| 指标 | 符号 | 定义 | 目标值 |
| --- | --- | --- | --- |
| 不变式违反次数 | `V` | E1 中 I1–I7 的累计违反数 | 0 |
| 总量误差率 | `ε_total` | E2 定义 | 逐项 = 0；整单作为对照 |
| 批次级误差 | `ε_batch` | E2 定义 | 同上 |
| 有效变更次数 | `N_eff` | 一次业务操作的库存/金额实际变动次数 | 1 |
| 负库存次数 | `N_neg` | `avail < 0` 的出现次数 | 0 |
| 重复入账次数 | `N_dup` | 同幂等键的台账记录数减一 | 0 |
| 残留状态量 | `R` | E5 注入后的非预期记录数 | 0 |

## 6. 预期结果与判定标准

| 实验 | 支撑假设 | 预期结论 | 若不符合预期的处理 |
| --- | --- | --- | --- |
| E1 | H1 | 违反次数为 0，机制在随机序列下不变式成立 | 定位首个违反点，作为机制缺陷在论文中如实报告并修正 |
| E2 | H2 | 逐项回补误差为 0；整单分摊在反向偏差 + 跨批次时误差显著 | 若整单无误差，说明 H2 需修正，改为报告两种粒度的适用边界 |
| E3 | H3 | 有效变更次数恒为 1 | 若出现重复入账，则幂等设计存在缺口 |
| E4 | H3 补充 | 负库存与重复入账均为 0 | 定位并发窗口，说明锁粒度是否需要收紧 |
| E5 | H1 补充 | 残留状态量为 0 | 定位事务边界缺失处 |

**结论的有效性条件**：即使全部实验通过，也只说明机制在**单实例、单库、可信进程内**成立。这一边界须在论文局限章节明确陈述。

## 7. 效度威胁分析

| 类型 | 威胁 | 缓解措施 |
| --- | --- | --- |
| **内部效度** | 测试环境为单机单实例，与生产的多实例部署不同，悲观锁的有效性可能被高估 | 在局限中明确；可补充多实例实验作为未来工作 |
| **内部效度** | 随机序列可能覆盖不到某些并发时序 | E4 采用固定并发度枚举而非随机，并辅以 `CountDownLatch` 对齐起跑点 |
| **构念效度** | 以「不变式成立」代理「一致性正确」，二者不完全等价 | 不变式由业务规则推导，并在论文中给出推导过程而非直接断言 |
| **外部效度** | 结论依赖 MySQL 的 InnoDB 行锁语义，换用其他存储引擎可能不同 | 明确实验基于 MySQL 8.0 InnoDB |
| **结论效度** | E2 每组合 30 次抽样，统计功效有限 | 报告置信区间；对显著差异补充扩大样本的复核实验 |
| **构念效度** | 未接入真实支付渠道，支付成功由人工确认模拟 | 说明支付适配层为可替换边界，一致性机制不依赖渠道实现 |
