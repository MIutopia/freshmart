## 一、实验目的

验证生鲜电商在「按重量计价、下单只得预估克数」这一约束下，所设计的**金额与库存双维度一致性机制**是否成立。具体回答三个研究问题：

| 编号 | 研究问题 |
| --- | --- |
| RQ1 | 在多样化的订单结构与偏差组合下，一致性不变式是否始终成立？ |
| RQ2 | 差额按整单分摊与按订单项逐项回补，两种粒度有何差异？ |
| RQ3 | 重复提交与并发操作下，幂等设计与唯一约束是否足以避免重复入账？ |

## 六、关键发现

### 发现一：实验暴露了一处实现缺陷（已修复）

**现象**：E1-3（实际克数等于预估克数）与 E2 的多个用例在初次运行时抛出 `409 CONFLICT "user wallet is unavailable"`。

**根因**：结算策略对差额的判定为

```java
if (difference.signum() <= 0) {
    return new Settlement(SettlementAction.REFUND_USER, difference.abs(), BigDecimal.ZERO);
}
```

**差额为零时也进入退款分支**，进而要求用户钱包账户必须存在，并会写入一条 0 元钱包流水。而实验库中 `wallet_accounts` 为空表，因此整笔称重调整被拒绝。

**影响**：金额无差额时不应存在任何资金动作。原实现使一次纯粹的「库存校准」操作产生了对钱包的**无谓依赖**，并在有钱包时留下 0 元流水记录。

**修复**：在结算入口增加零差额短路，既不退款也不记账：

```java
// 金额无差额时不存在资金动作：既不退款也不记账，避免产生 0 元流水与无谓的钱包依赖
if (settlement.refundAmount().signum() == 0 && settlement.absorbedAmount().signum() == 0) {
    markSettled(order.id(), "WEIGH-NO-DIFF-" + order.id());
    return;
}
```

> 这是本次实验最有价值的产出：**实验设计本身发现了实现中的真实缺陷**，而非仅仅验证既有代码。

### 发现二：假设 H2 部分被证伪，但得到了更有价值的结论

原假设：整单分摊在「跨多批次且偏差方向相反」时会产生可测量的克数误差，而逐项回补误差为零。

**实测结果**：两种粒度在**总量上都无损**。整单分摊之所以没有误差，是因为实现采用了「按预占比例计算、最后一批兜底剩余」的策略——取整余数被最后一批吸收，因此 `ε_total = 0` 在 7 批次场景下同样成立（E2-3）。

**但这不意味着两种粒度等价**。真正的差异在**批次级归属**（E2-4 对照）：

| 场景 | 整单模式 | 逐项模式 |
| --- | --- | --- |
| 项 1 占批次 A（变重 100 克）<br>项 2 占批次 B（变轻 100 克） | 净差额为 0 → **两个批次都不变化** | 批次 A 扣减 100 克、批次 B 退回 100 克 |

**结论修正**：整单模式虽然保持了总量守恒，却把某一订单项的偏差**抵消或摊派到其他订单项的批次上**，使批次账实与真实拣货结果不符；逐项模式的批次变化只由使用该批次的订单项决定，与实际拣货结果一致。

这从「误差」问题转化为「**批次归属精度**」问题，是可量化、可论证的结论，对论文而言比原假设更有价值。

### 发现三：假设 H1 与 H3 成立

- **H1 成立**：20 轮随机生成的订单结构（1–4 个订单项、每项跨 1–3 批次、偏差方向与幅度随机）下，I1、I2、I6、I7 全部成立，违反次数为 0。
- **H3 成立**：三种重复与并发场景下，「有效变更次数」恒为 1。机制上由两层保障：先查幂等键返回首次结果（顺序重放路径），唯一约束兜底拦截竞态（并发路径）。

## 八、局限

1. **单实例、单库环境**：实验在单机 MySQL 上执行，悲观行锁与条件更新的有效性可能被高估，结论不外推到多实例部署。
2. **前置数据由 SQL 构造**：订单与批次分配未经过完整下单链路，因此本实验的结论限于「称重与回补机制」，不涵盖下单与支付链路的正确性（该部分由 96 项端到端测试覆盖）。
3. **并发样本有限**：并发实验仅覆盖 10 线程、单一竞争点，未做并发度扫描与重复轮次统计。
4. **未接入真实支付渠道**：退款路径依赖钱包账户，真实微信退款不在本实验范围内。
5. **未做性能度量**：本实验关注正确性而非吞吐与延迟。
