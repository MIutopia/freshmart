# 交易与模拟支付

首期交易使用 `freshmart_trade` 记录交易单、商家子订单、订单项、库存预占、支付单和费用台账。商品、批次和配送任务分别仍归属商家库与配送库。

## 创建交易

交易请求传入配送区域、地址快照与按克计量的商品行，并且必须携带 `Idempotency-Key`。服务端读取已上架商品、市场价、商家价、仓配规则和批次库存；前端价格不会参与结算。

1. 依据配送区域和分类仓配优先级为每个商品选择仓库。
2. 同一商家存在多个不同仓库时，拒绝该交易，避免跨仓拆分。
3. 按商家生成履约子订单，并分别计算商品金额和配送费。
4. 以先进临期批次优先顺序锁定库存，并将预占记录设置为平台规则 `inventory.reservation.minutes`（默认 15 分钟）后到期。
5. 保存用户价、商家应收价和平台价格补贴快照；用户价不高于市场价，商家价上限由 `product.market.price.max.markup.rate` 规则控制（默认 5%）。

## 个人收款码支付适配器

首期固定使用 `PersonalWechatQrPaymentAdapter`。`POST /api/payments/{tradeNo}/prepay` 通过统一支付适配器创建支付单，返回本机环境变量 `PERSONAL_WECHAT_QR_URL` 配置的收款码、支付单号、待支付状态和付款备注模板。用户转账时必须在备注中填写系统订单号；系统不会调用微信接口，也不会把收款码或密钥写入代码库。

付款核验也通过适配器统一封装：用户可提交转账截图（`POST /api/payments/{tradeNo}/proof`），管理员审核截图（`POST /api/admin/payments/{tradeNo}/verify-proof`），或管理员导入微信账单（`POST /api/admin/payments/bill-imports`）。只有人工审核或账单按订单号、金额和收入方向匹配成功，支付单才会返回统一状态 `PAID`。金额不一致、备注缺失、匹配失败分别记录标准化错误状态和核验记录，不得直接推进订单。

管理员确认到账后，交易服务消费适配器返回的 `PAID` 结果，扣减已预占批次库存、交易单改为 `PAID`、商家子订单改为 `WAITING_PICKING`，并在配送库创建一条状态为 `WAITING_ASSIGNMENT` 的任务。适配器不负责库存、优惠券、积分和配送业务；该操作通过同一 MySQL 实例的单连接事务执行，生产拆库后须改为事件 outbox 与补偿机制。

账单导入会保存导入批次和原始流水。未找到订单、金额不一致、备注缺失、系统已支付但账单无记录等情况写入对账差异表，由管理员处理后留存解决人和时间。

配送费规则 `freight.free.threshold` 和 `freight.standard.fee` 在每次下单时从核心库 `platform_rules` 读取，规则不可用时回退到应用配置默认值。

库存预占释放任务每 60 秒扫描一次到期交易；到期后回退批次的 `reserved_grams`、将预占记录标记为 `RELEASED`、取消交易和子订单，并将待支付个人收款码支付单标记为 `EXPIRED`。可通过 `INVENTORY_RELEASE_INTERVAL_MS` 调整扫描间隔。

余额支付已接入：`POST /api/payments/{tradeNo}/confirm-balance` 按交易应付金额扣款，记录钱包流水并复用库存扣减、配送任务、优惠券核销和积分发放流程。所有售后申请通过统一退款适配器创建；个人收款码订单客服审核通过后只生成 `PENDING_MANUAL_REFUND` 人工退款工单，不立即把原订单标记为已退款。管理员完成微信转账后调用 `POST /api/admin/refunds/{refundId}/complete-manual`，适配器返回 `MANUAL_REFUND_COMPLETED` 后才更新退款单、原订单、佣金、积分和库存处置；转账失败调用 `POST /api/admin/refunds/{refundId}/fail-manual` 并保留失败原因。余额订单仍可在统一接口下即时退回钱包。微信商户号签名回调、原路退款回调仅作为后续适配器草案，不在首期范围。
