# 多库数据架构

首期将单一 MySQL 实例按业务数据所有权拆分为五个数据库。它们仍部署在本机 `127.0.0.1:3307`，但使用独立 Schema，避免商家、用户、配送、交易与日志表互相直接写入。

| 数据库 | 数据所有权 | 核心表 |
| --- | --- | --- |
| `freshmart_user` | 用户、账号、角色、地址、余额 | `users`、`user_role_assignments`、`user_addresses`、`wallet_accounts`、`wallet_transactions` |
| `freshmart_merchant` | 商家、入驻、商品、仓库、批次库存 | `merchants`、`merchant_applications`、`products`、`warehouses`、`inventory_batches` |
| `freshmart_delivery` | 区域、配送员、派单、绩效 | `delivery_zones`、`rider_profiles`、`delivery_tasks`、`rider_performance_daily` |
| `freshmart_trade` | 交易、子订单、支付、费用台账 | `trade_orders`、`orders`、`payment_orders`、`fee_ledgers` |
| `freshmart_log` | 审计、站内消息、跨库事件 | `audit_logs`、`inbox_messages`、`integration_outbox` |

## 跨库规则

- 只以 `user_id`、`merchant_id`、`warehouse_id`、`delivery_zone_id`、`trade_id` 和 `order_id` 等业务 ID 关联，不建立跨库外键。
- 常规写操作只在所属库内开启本地事务。首期交易履约因五个 Schema 同处一个 MySQL 实例，使用交易库连接的跨 Schema 本地事务原子锁定库存、写入交易并创建配送任务；独立部署后必须切换为 `freshmart_log.integration_outbox` 和补偿重试。
- `fee_ledgers` 是费用事实台账，记录配送费、平台佣金、平台补贴、退款和余额变化的正负方向；不得以订单金额字段替代费用明细。
- 商家商品、仓库、批次库存只归属于 `freshmart_merchant`；配送任务只归属于 `freshmart_delivery`，不允许其他库直接修改其状态。

## 初始化

使用 MySQL 管理员账号执行 `backend/scripts/bootstrap-database.sql` 创建基础库和应用账号后，再执行 `backend/scripts/bootstrap-domain-databases.sql`。后者创建五个业务库、开发环境授权、各库的首批表，以及用户、商家、配送员各 10 个本地测试账号。

运行时代码以五个业务库为唯一数据归属：认证、商家目录、交易履约、配送和日志分别读取对应卫星库；`freshmart` 只保留平台规则、Flyway 历史及尚未迁移的兼容遗留表，不再作为卫星业务表的运行时来源。

`V27__align_satellite_schema_contract.sql` 将历史遗漏的用户权益、商家营销/仓配规则、交易预占/小票/退款/称重和日志 SVG 字段补齐到卫星库。`DomainSchemaReadinessVerifier` 在应用启动阶段一次性检查必需表和关键列，发现结构不完整时直接列出全部缺项并阻止定时任务启动，避免运行时逐个暴露 SQL 异常。

新环境仍应先执行多库初始化脚本；已有环境升级时由 Flyway 执行 V27。脚本和迁移必须保持同一结构基线，新增领域表只能落在所属卫星库。
