# 生鲜电商称重结算中金额与库存双维度一致性保障机制的设计与验证

## 摘要

生鲜商品按重量计价，下单时只能确定预估克数，实际交付重量须在分拣称重后才能确定。这一特性使系统必须在金额与库存两个维度上同时维护正确性：前者要求明确"预估金额与实际金额之差"的归属，后者要求把"实际出库克数与预占克数之差"回补到具体批次。现有工程实践多只处理金额差额，忽略克数回补，导致批次账实长期偏离且难以察觉。

本文以一个多商家生鲜电商系统 FreshMart 为对象，设计并验证一套覆盖"预占—核销—回补"全生命周期的一致性机制。本文首先以七条一致性不变式（I1–I7）对机制进行形式化刻画，并给出子订单与库存预占的状态机模型；随后实现覆盖不变式随机回归（E1）、分摊粒度对照（E2）与幂等性（E3）三组实验，共 10 项用例，在真实 MySQL 数据库上执行。

实验得到三项结果。第一，在 20 轮固定随机种子生成的订单结构（1–4 个订单项、每项跨 1–3 批次、偏差方向与幅度随机）下，I1、I2、I6、I7 的违反次数为 0，验证了机制的鲁棒性。第二，原有假设"整单分摊在跨多批次且偏差方向相反时会产生可测量的克数误差"被证伪：由于分摊算法采用了"按预占比例计算、最后一批兜底剩余"的兜底策略，两种粒度在总量上均无损，即使跨 7 个批次连续取整，回补总量仍精确等于差额。两种粒度的真实差异不在总量而在**批次级归属**——整单模式下净差额为零时各批次均不变化，某一订单项的偏差会被其他项抵消；逐项模式则把偏差如实回补到各订单项自身占用的批次，与真实拣货结果一致。据此本文将论文核心论点由"误差大小"修正为"批次归属精度"。第三，顺序重放、10 线程并发同键、同实体异键三种重复与并发场景下，有效变更次数恒为 1。

本文的另一项产出是：实验本身发现了一处真实实现缺陷——结算策略在差额为零时仍进入退款分支，进而要求用户钱包账户存在并写入一条 0 元流水。该缺陷经定位后已修复。这一过程表明，以不变式驱动的实验设计不仅能验证既有实现，也能反向发现设计盲区。

**关键词**：生鲜电商；称重结算；数据一致性；不变式；幂等性；批次追溯

## 第一章 绪论

### 1.1 研究背景

生鲜农产品电商在过去十年间成为零售数字化的重要方向。与标准工业品相比，生鲜品类具有三个显著特征，这三个特征共同决定了其信息系统设计的特殊性。

**第一，计价单位是重量而非件数。** 蔬菜、水果、肉类等品类的价格以"元/千克"表示，交易金额等于实际重量与单价的乘积。消费者下单时无法精确预知自己要买多少克，商家也无法在下单时确定每一份的实际重量，因此订单金额在创建时只能是**预估值**。

**第二，实际重量必须在分拣环节才能确定。** 从下单到分拣存在时间差，期间商品还会经历损耗与水分蒸发。订单履约链条为"下单支付 → 仓库分拣称重 → 配送 → 送达"，实际重量要到分拣称重那一刻才产生。这意味着**支付金额与实际应收金额必然存在差额**，差额可能是正（实际更重，用户需补付）也可能是负（实际更轻，需退款）。

**第三，库存必须以批次为单位追溯。** 生鲜商品具有保质期，同一商品的不同批次进货时间与过期时间不同，促销策略也不同（临期批次需降价清仓）。因此库存管理不是"某商品有 100 千克"这样的标量，而是"某商品在 A 批次有 60 千克、B 批次有 40 千克"这样的向量。下单时必须选定具体批次并预占，出库时必须从被预占的批次扣减。

三个特征叠加后，产生了一个容易被忽视的缺口：**金额差额与克数差额是两个独立维度，必须分别处理**。

### 1.2 问题提出

考虑一个典型场景：用户下单购买 1 千克番茄，系统按预估重量计算并收取 9.5 元，同时从 A 批次预占 1000 克。分拣时实际称重为 1100 克，此时需要处理两件事：

1. **金额维度**：预估 9.5 元、实际应收 10.45 元，多出的 0.95 元由谁承担？是向用户补收、由平台吸收，还是转人工复核？行业内普遍设有"平台误差承担上限"，超出上限则转人工。
2. **库存维度**：多出的 100 克从哪里来？答案是从 A 批次再扣减 100 克。如果只处理金额而不处理克数，A 批次的账面可用量就会比实际多出 100 克。

现有工程实践与文献多聚焦于第一个维度——支付金额的对账与差错处理已经相当成熟，对账系统、差错池、人工核销流程等都有标准做法。而第二个维度**缺少系统性讨论**：库存克数的回补往往被简化为"总量对齐"，即保证"所有批次扣减量之和等于实际出库量"即可。

但本文的实验表明，**总量对齐并不充分**。当订单包含多个订单项、每项占用不同批次时，仅保证总量对齐会导致批次级的账实偏离：某一订单项的偏差可能被其他订单项的相反偏差抵消，从而在总量上"看起来正确"，而实际的批次库存已经不准。对于需要按批次追溯保质期与促销策略的生鲜电商而言，这种偏离会直接导致临期商品误判、损耗统计失真与促销选品错误。

因此，本文要回答的核心问题是：**在生鲜按重量计价的约束下，如何设计并验证一套同时保证金额与库存（含批次级归属）一致性的机制？**

围绕这一核心问题，本文提出三个具体研究问题：

| 编号 | 研究问题 |
| --- | --- |
| **RQ1** | 在"预占 → 支付核销 → 称重调整 → 退款回补"的完整生命周期中，如何定义并保证金额与库存的双维度一致性？ |
| **RQ2** | 称重差额按**整单分摊**与按**订单项逐项回补**，两种粒度在克数误差与批次偏差上的差异有多大？ |
| **RQ3** | 在重复提交与并发操作的条件下，全链路幂等设计与悲观锁机制是否足以避免重复入账与负库存？ |

### 1.3 研究内容与贡献

本文以自主实现的多商家生鲜电商系统 FreshMart 为研究对象。该系统采用 Java 17 与 Spring Boot 3 构建，包含 91 个主源码文件、47 个 Flyway 数据库迁移与 102 张数据表，覆盖用户端、商家端、配送端与平台管理后台四类业务端。本文在此基础上完成以下工作。

**贡献一：给出称重场景下的一致性形式化刻画。** 本文提出七条一致性不变式（I1–I7），覆盖非负性、预占约束、批次守恒、订单项守恒、金额守恒、粒度一致性与分摊无损性七个方面，并给出子订单与库存预占的状态机模型。这些不变式不仅是设计约束，也直接作为后续实验的判定依据，使实验结论可被机械验证而不依赖主观判断。

**贡献二：实现并执行三组一致性实验，得到与初始假设不同的结论。** 本文实现 E1（不变式随机回归）、E2（分摊粒度对照）、E3（幂等性）共 10 项用例，在真实 MySQL 数据库上执行，全部通过。其中 E2 的结果**证伪了本文的初始假设**：由于分摊算法采用了"最后一批兜底剩余"的兜底策略，整单分摊与逐项回补在总量上均无误差。本文如实报告这一结果，并据此将核心论点修正为更具解释力的"批次归属精度"——两种粒度的真实差异不在总量，而在于偏差是否被如实回补到各订单项自身占用的批次。

**贡献三：以实验驱动发现并修复了一处实现缺陷。** 实验过程中，E1 与 E2 的多个用例报出 `409 user wallet is unavailable`。定位表明，结算策略在金额差额为零时仍进入退款分支，进而要求用户钱包账户必须存在，并会写入一条 0 元流水。本文将这一发现作为"以不变式驱动的实验设计具备缺陷发现能力"的实证，而非仅仅作为一次偶然的调试经历。

### 1.4 论文组织

本文其余部分组织如下。第二章回顾分布式事务、库存一致性与幂等设计的相关工作，并指出现有研究的缺口。第三章给出系统架构、七条不变式、状态机模型与三阶段一致性机制的设计。第四章报告三组实验的环境、方法、数据与结果。第五章讨论核心论点、效度威胁与局限。第六章总结全文并展望未来工作。

## 第二章 相关工作

### 2.1 分布式事务与一致性模型

在跨库、跨服务的场景中，强一致的分布式事务代价高昂，业界普遍转向**最终一致性**方案。Gray 与 Reuter 在经典著作中系统阐述了事务的 ACID 语义及其实现机制，为后续研究奠定了理论基础[1]。Bernstein 等人则对并发控制与恢复算法做了完整的形式化处理，其中两阶段锁（2PL）与多版本并发控制（MVCC）成为主流数据库的基石[2]。

Garcia-Molina 与 Salem 提出的 **Saga** 模式将长事务拆解为一系列本地事务，并为每个本地事务配备补偿操作，在失败时逆序执行补偿[3]。Saga 的贡献在于承认"长事务无法保持原子性"，转而以补偿换取可用性。但补偿语义要求每个正向操作都存在业务上有意义的逆操作，这一前提在本场景中并不总是成立——批次库存的扣减可以被退回，但"用户已经吃掉的商品"无法退回。

Brewer 提出的 CAP 猜想及其后续的形式化证明指出，在存在网络分区时，一致性与可用性不可兼得[4][5]。这为本文的工程选择提供了理论依据：本文系统运行于单一数据库实例内，跨库操作通过应用层事务管理器协调，因此在**不涉及网络分区的前提下**可以选择强一致策略，而不必引入最终一致性的复杂度。

Helland 则从实践角度指出，大规模系统中应当避免跨实体的原子事务，转而依赖幂等操作与去重机制[6]。本文的设计在这一点上与之一致：对于确实需要跨库的操作，本文采用"本地事务 + 幂等键 + 唯一约束"的组合，而非分布式事务。

### 2.2 库存一致性

库存一致性是电商系统的经典问题，但其讨论重心长期集中在**超卖控制**上。常见做法包括数据库行锁、条件更新（乐观锁）、Redis 原子操作与队列串行化。

条件更新是一种被广泛采用的轻量方案：将扣减操作表述为 `UPDATE ... WHERE available >= ?` 的形式，由数据库保证判断与更新在同一语句内原子完成，影响行数为零即表示库存不足。这一做法避免了显式加锁，但要求业务层正确处理"更新失败"这一正常路径而非异常。

Kleppmann 在讨论数据密集型应用设计时指出，分布式系统中的**不变式维护**应当尽量下沉到单点**，即把需要原子性保证的约束交给单一数据库节点处理，避免应用层协调[7]。本文的设计遵循这一原则：库存扣减的唯一性由数据库唯一约束与条件更新保证，应用层只负责编排。

然而，上述工作的共同局限在于**把库存视为标量**。无论是超卖控制还是库存对账，讨论的都是"某商品的总量是否正确"，而未涉及"某一批次的量是否正确"。在生鲜、医药等需要按批次追溯保质期的场景中，标量库存模型不足以刻画真实的库存状态。Fowler 在讨论企业应用架构时提出过"库存应表示为可追踪的实体集合"的观点[8]，但未给出具体的守恒模型与验证方法。

### 2.3 幂等设计

幂等性是分布式系统的核心工程手段之一。Helland 将幂等操作列为构建大规模系统的关键模式，强调"使操作可重复执行而不产生额外副作用"比"保证操作只执行一次"更现实[6]。

工程上实现幂等的常见手段有三类：**幂等键去重**、**状态机前置校验**与**唯一约束**。

1. **幂等键去重**：客户端为每次写操作生成唯一键，服务端记录已处理的键，重复请求直接返回首次结果。
2. **状态机前置校验**：为业务对象定义合法状态转换，非法转换返回冲突而非静默忽略。
3. **唯一约束**：在数据库层对业务实体加唯一索引，使重复写入在存储层被拦截。

三类手段的可靠性不同。幂等键去重依赖应用层的"查询—写入"两步操作，在并发下存在竞态窗口；唯一约束由数据库保证，可在竞态下提供最终保障。因此**稳健的实现应同时使用两者**，前者提供正常路径的效率，后者提供竞态下的正确性。

本文在这一点上做了明确设计：所有写操作携带幂等键，同时关键业务表建立唯一索引（例如每个子订单最多一条称重调整记录由 `uk_weighing_order` 约束）。第四章的实验 E3 专门验证了这一组合在顺序重放与并发同键下的有效性。

### 2.4 现有工作的不足与本文定位

综合上述工作，可以识别出三个缺口。

**缺口一：称重场景下的库存一致性缺少系统讨论。** 现有库存一致性研究以标量库存为对象，未处理"按重量计价、下单只得预估、实际重量后置"这一特殊约束。而这正是生鲜电商的常态。

**缺口二：批次级归属精度未被作为独立问题提出。** 即使接受"按批次管理库存"的做法，现有讨论也只要求"总量对齐"，未意识到多订单项场景下相反偏差会互相抵消，导致总量正确而批次失真。

**缺口三：一致性机制缺少可机械验证的判定标准。** 多数工程实践以"测试通过"作为正确性证据，而测试用例的覆盖范围依赖人工设计，难以覆盖随机组合。以形式化不变式作为判定依据的做法在工程论文中尚不常见。

本文针对这三个缺口展开：以七条不变式给出可机械验证的判定标准（对应缺口三），在真实的按重量计价场景中设计和验证机制（对应缺口一），并通过对照实验揭示了批次级归属精度这一此前未被提出的问题（对应缺口二）。

## 第三章 系统与机制设计

### 3.1 系统架构与多库分域

FreshMart 采用多库分域架构。业务数据按领域边界拆分为五个卫星库，主库仅保留平台规则配置与迁移历史：

| 数据库 | 职责 | 主要数据 |
| --- | --- | --- |
| `freshmart` | 平台规则与迁移历史 | 平台规则、Flyway 历史 |
| `freshmart_user` | 用户域 | 账号、角色、钱包、积分 |
| `freshmart_merchant` | 商家域 | 商家、仓库、商品、分类、批次、入库单 |
| `freshmart_trade` | 交易域 | 交易单、子订单、订单项、批次分配、称重调整、退款、台账 |
| `freshmart_delivery` | 配送域 | 配送区域、配送任务、骑手绩效 |
| `freshmart_log` | 日志域 | 审计日志、资金状态流水 |

**分域的依据是变更频率与访问模式**：交易域写入最频繁且需要强一致，日志域只追加不修改，配置域几乎不变。分域后各域可使用独立的连接池与事务管理器，避免一个域的长事务阻塞其他域。

多库带来的风险是**结构漂移**：某个卫星库的表结构与代码预期不一致时，故障往往在运行期才暴露。为此系统在启动时执行结构校验——`DomainSchemaReadinessVerifier` 会检查五个卫星库的表与关键列是否存在，缺失即拒绝启动。这一"快速失败"策略把结构问题从运行期提前到了启动期。

跨库操作通过应用层事务管理器协调。以称重调整为例，它需要同时写入交易域（称重记录）与商家域（批次克数），系统为两个域配置独立的事务管理器，并在服务方法上显式声明事务管理器名称，通过 Spring 的事务同步保证两者在同一个逻辑事务内提交或回滚。

### 3.2 形式化建模：符号定义与一致性不变式

为精确描述一致性要求，首先定义符号。设 `b` 为某个库存批次，`o` 为某个子订单：

| 符号 | 含义 |
| --- | --- |
| `avail(b)` | 批次 `b` 的可用克数 |
| `resv(b)` | 批次 `b` 的已预占克数 |
| `in(b)` | 批次 `b` 的累计入库净重 |
| `shipped(b)` | 批次 `b` 的累计实际出库克数（以订单项实际称重为准，未称重时取预占克数） |
| `restocked(b)` | 批次 `b` 的累计退货回补克数 |
| `Δ(b)` | 批次 `b` 的累计称重回补量（正数补扣、负数退回） |
| `prepaid_grams(o)` | 子订单 `o` 的预估克数（即订单项预占量之和） |
| `actual_grams(o)` | 子订单 `o` 的实际称重克数 |

在此基础上，本文提出七条一致性不变式。

```text
I1（非负性）    ∀b:  avail(b) ≥ 0  ∧  resv(b) ≥ 0
I2（预占约束）  ∀b:  resv(b) ≤ avail(b)
I3（批次守恒）  ∀b:  avail(b) + resv(b) + shipped(b) − restocked(b) + Δ(b) = in(b)
I4（订单项守恒）∀o:  Σ_items actual_grams = weighing_adjustments.actual_grams
I5（金额守恒）  ∀o:  refund_amount + absorbed_amount = max(actual − prepaid, 0)
                    且当 actual < prepaid 时  refund_amount = prepaid − actual
I6（粒度一致性）∀o:  Σ_items inventory_adjust_grams = inventory_adjust_grams(整单记录)
I7（分摊无损）  ∀o:  Σ_batches share(b) = actual_grams − prepaid_grams
```

**I1 与 I2 是安全底线**：负的可用克数意味着系统承诺了不存在的库存，这是最严重的库存缺陷。I2 进一步要求预占量不得超过可用量，防止同一批次的可用部分被重复承诺。

**I3 是批次守恒的核心**。它要求任一批次的可用量、预占量、已出库量、已回补量与称重调整量之间的关系可以精确闭合。这条不变式把"账面"与"实物"联系起来：`in(b)` 是实际入库的净重，等式右侧是恒定的事实，左侧的每一项都是系统维护的账面值，因此等式成立意味着账面与实物一致。

**I4 与 I5 覆盖金额维度**。I4 要求整单的实际克数由各订单项汇总而来，不允许出现"整单有实际重量但订单项没有"的情形。I5 要求金额差额被完整分配给退款与平台承担两个科目，且当实际低于预估时退款额必须等于差额本身，不允许截留。

**I6 与 I7 是本文的重点**，也是后面实验的核心判定依据。I6 要求订单项级的回补量之和等于整单记录的回补量，保证两个层级的口径不矛盾；I7 要求分摊到各批次的份额之和精确等于总差额，不允许因逐批取整而丢失克数。

**I7 是实践中最易出错的一条。** 直觉上的实现是这样的：差额为 Δ，各批次预占量为 `g₁, g₂, …, gₙ`，则各批次应分摊 `Δ · gᵢ / Σg`。但这一算式的结果未必是整数，而克数必须是整数。若对每个批次独立四舍五入，`Σ round(Δ · gᵢ / Σg)` 未必等于 Δ。例如 Δ = 100、`g = (143, 143, 143, 143, 143, 143, 142)` 时，各批次应分摊 14.33 克左右，独立取整后累计可能与 100 相差数个克数。

本文采用的兜底策略是：**前 n−1 个批次按比例取整，最后一个批次承担剩余量**，即

```text
share(bᵢ) = round(Δ · gᵢ / Σg)            i = 1..n−1
share(bₙ) = Δ − Σ_{i<n} share(bᵢ)
```

这一策略保证 I7 恒成立而不依赖巧合。该策略的实现位于 `WeighingAdjustmentService.applyGramDifference(...)`，并在实验 E2 中通过跨 7 批次的场景专门验证。

### 3.3 状态机模型

状态机是"非法操作应被拒绝"这一要求的载体。在本场景中，最需要约束的是**称重调整的入口**与**库存预占的生命周期**。

**子订单状态机**如下：

```text
PENDING_PAYMENT ──支付成功──▶ WAITING_PICKING ──拣货──▶ PICKED ──送达──▶ DELIVERED
        │                                                    │
        └──超时/取消──▶ CANCELLED                             └──退款完成──▶ REFUNDED
```

**称重调整只允许在 `WAITING_PICKING`、`PICKED`、`DELIVERED` 三个状态下提交**。理由如下：`PENDING_PAYMENT` 状态下用户尚未付款，不存在"实收与预估之差"；`CANCELLED` 与 `REFUNDED` 状态下订单已终止，调整无意义。同时，每个子订单最多允许一条称重调整记录，由唯一索引 `uk_weighing_order` 在数据库层保证。

**库存预占状态机**如下：

```text
ACTIVE ──支付成功（核销）──▶ 已扣减 avail 与 resv
   │
   └──超时未支付（释放）──▶ RELEASED（仅扣减 resv）
```

两条转换路径的语义不同：**核销**同时扣减可用量与预占量（因为商品真的要被发出去了），而**释放**只扣减预占量（商品回到可用池）。区分二者的必要性在于：若释放时误用核销逻辑，可用量会被多扣一次，导致库存凭空减少。

### 3.4 三阶段一致性机制

综合上述不变式与状态机，本文设计的一致性机制可归纳为三个阶段。

**阶段一：预占。** 用户下单时，系统按预估克数从批次扣减可用量并增加预占量，同时记录批次分配明细。此阶段需保证两点：条件更新 `WHERE available_grams >= ?` 保证不会超卖；批次分配明细入库，为后续回补提供依据。

**阶段二：核销。** 支付成功后，系统同时扣减可用量与预占量，标记预占记录为已核销。此阶段的关键是**只允许核销一次**，通过预占记录的状态前置校验与行锁保证。

**阶段三：回补。** 分拣称重后，系统按实际克数与预占克数之差调整批次库存。这是本文的核心环节，其设计要点有三：

1. **金额与克数分离处理**。金额差额按"平台误差承担上限"规则判定为退款用户、平台吸收或转人工复核；克数差额则始终按实际值回补，不受金额规则影响。二者互不干扰。
2. **支持两种粒度**。既可提交整单实际克数（按订单整体分摊），也可提交逐项实际克数（按订单项各自分摊）。
3. **分摊无损**。无论哪种粒度，都采用 3.2 节的兜底策略保证 I7。

### 3.5 幂等与并发控制

系统采用三种互补手段应对重复与并发。

| 手段 | 实现位置 | 作用 |
| --- | --- | --- |
| 幂等键去重 | 各业务表 `idempotency_key` 唯一索引 + 写入前查询 | 顺序重放返回首次结果 |
| 悲观行锁 | 13 处 `SELECT ... FOR UPDATE` | 串行化同一实体的并发修改 |
| 条件更新 | 批次扣减 `WHERE available_grams >= ?` | 库存不足时影响行数为 0，触发回滚 |

三者的分工是明确的：**幂等键处理"用户重复点击"，悲观锁处理"同一实体的并发修改"，条件更新处理"资源不足时的正确拒绝"**。任何单一手段都不够：幂等键无法处理不同键指向同一实体的竞态（这正是实验 E3-c 验证的场景，由唯一约束兜底），条件更新无法处理"重复写入两条语义相同的记录"。

此外，条件更新的失败被设计为**正常路径而非异常**。当库存不足时，条件更新影响行数为 0，服务层据此抛出 409 冲突。这是"正确的拒绝"，而非系统缺陷——这一区分在实验 E4 的度量设计中有明确体现。

为避免实验数据污染既有数据，所有实验数据带 `EXP-` 前缀，并在每个用例结束后按前缀精确清理。

### 4.4 E1 不变式随机回归

#### 4.4.1 实验方法

E1 通过随机组合检验机制的鲁棒性。每轮实验随机生成一个订单结构：

- 订单项数：1 至 4；
- 每项跨越的批次数：1 至 3；
- 每项预占克数：500 至 1000 克；
- 偏差幅度：不超过预占克数的 20%，方向随机（变重或变轻）。

生成结构后，以逐项粒度提交称重，随后校验 I1、I2、I6、I7 四条不变式。实验共执行 20 轮。

此外，E1 包含两个边界用例：**全部订单项都变轻**（验证回补方向为退回而非补扣），以及**实际克数恰好等于预估克数**（验证零差额路径不改变任何库存）。

#### 4.4.2 实验结果

```text

Test: allLighterItemsReturnGrams ............ PASS
Test: equalGramsLeaveInventoryUntouched ..... PASS

Tests run: 3, Failures: 0, Errors: 0
```

20 轮随机回归的全部轮次均执行完毕，**I1、I2、I6、I7 的违反次数为 0**。假设 H1 成立。

#### 4.4.3 一个值得说明的现象

在"全部变轻"用例的首次执行中，本文的断言预期失败：断言期望两个批次各退回 150 克（即把 300 克总差额在批次间均摊），而实际结果是批次 A 退回 100 克、批次 B 退回 200 克。

经核对，**系统行为是正确的，失败的是本文的断言**。系统按订单项各自执行回补：订单项 1 变轻 100 克，只影响它自己占用的批次 A；订单项 2 变轻 200 克，只影响批次 B。这正是逐项回补的设计意图。

这一插曲在方法论上有所启示：当实验结果的预期与实际不符时，**首先应当核对的是预期本身是否基于正确的理解**，而非直接判定实现有缺陷。

### 4.5 E2 分摊粒度对照

#### 4.5.1 实验方法

E2 是本文的核心实验，直接对照两种分摊粒度的行为。实验包含四个用例：

| 用例 | 场景 | 验证目标 |
| --- | --- | --- |
| E2-1 整单分摊无损性 | 2 个订单项跨 3 个批次，整单提交 2000 → 2200 克 | I7（整单模式） |
| E2-2 逐项口径一致性 | 同结构，项 1 变重 150 克、项 2 变轻 50 克 | I4、I6（逐项模式） |
| E2-3 跨 7 批次取整补偿 | 单订单项跨 7 个批次，1000 → 1100 克 | I7（多次取整） |
| E2-4 批次级分布对照 | 同偏差分别以两种粒度提交 | RQ2 核心对照 |

#### 4.5.2 实验结果

```text
Test: wholeOrderAllocationIsLossless ................. PASS
Test: itemWeighingIsConsistentWithOrderTotals ........ PASS
Test: allocationAcrossManyBatchesRemainsExact ........ PASS
Test: granularitiesDifferInBatchLevelDistribution .... PASS

Tests run: 4, Failures: 0, Errors: 0
```

**关于总量误差（E2-1、E2-3）**：两种粒度的回补总量均精确等于差额。特别是在 E2-3 中，1000 克预占按 7 个批次分配为 143×6 + 142，存在天然取整余数；实际称重 1100 克时差额 +100 需按比例分摊 7 份。实测各批次扣减量之和为**精确的 100**，取整余数由最后一批兜底吸收。这验证了 3.2 节兜底策略的有效性，也**证伪了本文原假设中"整单分摊会产生可测量的克数误差"这一判断**。

**关于批次级归属（E2-4）**：这是本实验最具价值的发现。对照条件为：订单项 1 仅占用批次 A 且变重 100 克，订单项 2 仅占用批次 B 且变轻 100 克。两种粒度的结果如下表。

| 度量 | 整单模式 | 逐项模式 |
| --- | --- | --- |
| 净差额 | 0 | 0 |
| 批次 A 变化 | 0（不变） | −100 克（补扣） |
| 批次 B 变化 | 0（不变） | +100 克（退回） |
| 与真实拣货结果的一致性 | 不一致 | 一致 |

整单模式下，由于净差额为 0，**两个批次都不发生变化**。这意味着订单项 1 多拿的 100 克没有被补扣，订单项 2 少拿的 100 克也没有退回，两个偏差互相抵消了。虽然总库存正确，但**批次 A 的账面比实际多 100 克，批次 B 的账面比实际少 100 克**。

逐项模式下，偏差被如实回补到各自批次，批次账实与真实拣货结果一致。

### 4.6 E3 幂等性实验

#### 4.6.1 实验方法

E3 包含三个子场景。

| 场景 | 操作 | 期望 |
| --- | --- | --- |
| E3-a 顺序重放 | 同一幂等键连续提交 5 次 | 有效变更恰好 1 次，且每次返回同一调整标识 |
| E3-b 并发同键 | 10 个线程用同一幂等键同时提交 | 恰好 1 次生效，其余转为冲突 |
| E3-c 同实体异键 | 同一订单用不同幂等键提交 | 恰好 1 次生效，其余被拒绝 |

并发场景采用 `ExecutorService` 配合 `CountDownLatch` 对齐起跑点，保证所有线程同时发起请求。**断言全部在事务提交后重新查询数据库获得，而非依赖接口返回值**——这一点很关键，因为接口返回值可能是缓存的结果，只有重新查询数据库才能确认实际变更次数。

#### 4.6.2 实验结果

```text
Test: sequentialReplayAppliesOnce ......... PASS
Test: concurrentSameKeyAppliesOnce ........ PASS
Test: differentKeysSameOrderRejected ...... PASS

Tests run: 3, Failures: 0, Errors: 0
```

| 场景 | 有效变更次数 | 称重记录数 | 批次变化 |
| --- | --- | --- | --- |
| E3-a 顺序重放 5 次 | 1 | 1 | 扣减一次 |
| E3-b 10 线程并发同键 | 1 | 1 | 扣减一次 |
| E3-c 同实体异键 | 1 | 1 | 扣减一次 |

三种场景下有效变更次数**恒为 1**，假设 H3 成立。

值得注意的是三个场景的拦截机制并不相同，这印证了 3.5 节"单一手段不够"的判断：

- **E3-a** 由幂等键查询拦截：重放请求命中已记录的幂等键，直接返回首次结果；
- **E3-b** 由唯一约束拦截：10 个线程可能同时通过幂等键查询（竞态窗口），但 `idempotency_key` 唯一索引使只有一个写入成功，其余抛出重复键异常并转为 409；
- **E3-c** 由订单级唯一约束 `uk_weighing_order` 拦截：不同幂等键绕过了幂等键检查，但"每个订单最多一条称重记录"的约束使其无法生效。

**如果只使用幂等键去重而不加唯一约束，E3-b 与 E3-c 都可能出现重复入账。** 这是本文设计中"两者并用"的直接依据。

### 4.8 关键发现

#### 4.8.1 发现一：实验发现了一处真实的实现缺陷

**现象**：E1 的"零差额"用例与 E2 的多个用例在首次运行时抛出 `409 CONFLICT "user wallet is unavailable"`。

**定位**：结算策略对差额的判定逻辑为

```java
if (difference.signum() <= 0) {
    return new Settlement(SettlementAction.REFUND_USER, difference.abs(), BigDecimal.ZERO);
}
```

问题在于 `<= 0` 这个条件：**差额为零时也进入退款分支**。进而，结算方法会执行"更新用户钱包余额"与"写入钱包流水"两个操作。前者在用户无钱包账户时影响行数为 0，随后的余额查询返回空，于是抛出冲突异常，整笔称重调整被拒绝。

**影响分析**：这一缺陷的影响有两层。表层影响是：一次纯粹的库存校准操作（金额无变化）却依赖用户钱包账户的存在，若钱包未开通则整个称重流程中断。深层影响是：当钱包存在时，每次零差额称重都会写入一条 0 元流水，污染资金流水记录。

**修复**：在结算入口增加零差额短路——既不退款也不记账，直接标记结算完成。

```java
// 金额无差额时不存在资金动作：既不退款也不记账，避免产生 0 元流水与无谓的钱包依赖
if (settlement.refundAmount().signum() == 0 && settlement.absorbedAmount().signum() == 0) {
    markSettled(order.id(), "WEIGH-NO-DIFF-" + order.id());
    return;
}
```

**方法论意义**：这一发现并非来自代码审查，而是来自**不变式驱动的实验设计**。E1 的"零差额"用例是被不变式体系推导出来的必要边界——既然存在 `actual = prepaid` 这一合法状态，就必须验证该状态下的行为。可以说，是**形式化建模的过程本身引导了缺陷的发现**。

#### 4.8.2 发现二：假设 H2 部分被证伪，但得到了更有价值的结论

**原假设**：整单分摊在"订单项跨多批次且偏差方向相反"时会产生可测量的克数误差，而逐项回补误差为零。

**实测结果**：两种粒度在**总量上都无损**。整单分摊之所以没有误差，是因为实现采用了"按预占比例计算、最后一批兜底剩余"的策略，取整余数被最后一批吸收，因此 `ε_total = 0` 在跨 7 批次的极端场景下同样成立。

**但这不意味着两种粒度等价**。E2-4 的直接对照表明，差异存在于**批次级归属**：当偏差方向相反且恰好相互抵消时，整单模式会使所有批次保持不动，实际情况却是某一批次被多拿了商品、另一批次少拿了商品。

**结论修正**：本文将论点从"误差量级"修正为"**批次归属精度**"。这不是一次失败的实验，而是一次有效的假设修正——它把一个无法证实的量化猜想，转化为一个有明确机制解释的定性结论，且该结论可被直接验证（E2-4 的对照即为验证）。

## 第五章 讨论

### 5.1 核心论点：批次级归属精度比总量守恒更重要

本文最重要的结论可以表述为：

> **在生鲜按重量计价的场景中，"总量守恒"不足以保证库存可信；真正决定库存可信度的是批次级归属的精度。**

支持这一论点的论证链条如下。

**第一，总量守恒在多订单项场景下会掩盖偏差。** 当订单包含多个占用不同批次的订单项时，各项偏差可能方向相反。只要总差额为零，整单模式便不做任何调整，而实际的批次库存已经偏离。

**第二，批次偏离的后果是可以具体描述的。** 生鲜电商的批次管理服务于三个业务目标：保质期管理（临期批次优先出库）、损耗统计（哪个批次损耗高）、促销选品（哪些批次需要降价清仓）。批次账面偏差会直接导致：临期判定落在错误的批次上，损耗统计失真，促销选品失误。这些都是可量化的业务损失。

**第三，逐项回补以可接受的代价解决了这一问题。** 逐项模式的代价是需要在分拣环节逐项采集实际重量并逐项提交，比整单模式多出若干次操作。但对于生鲜分拣这一本就逐项进行称重的作业环节而言，这一代价几乎为零——**称重动作本来就是逐项发生的，逐项回补只是把已经存在的信息如实记录**。

这一论点也解释了为什么"总量守恒"在工业品电商中是充分的，而在生鲜电商中不充分：工业品按件计价，订单项与库存单元一一对应，不存在"跨项抵消"的可能；生鲜按重量计价，订单项共享批次池，才产生了这一问题。

### 5.2 关于实验驱动的缺陷发现

发现一（4.8.1 节）值得单独讨论，因为它涉及方法论。

传统的工程质量保证手段是代码审查与测试用例。二者各有局限：代码审查依赖审查者的注意力与经验，难以系统性覆盖边界；测试用例的覆盖范围取决于设计者想到哪些场景。

本文的经验表明，**形式化建模可以补足这一局限**。当一致性要求被表述为七条不变式后，E1 的用例设计不再依赖"想到什么测什么"，而是被不变式体系推导出来：既然 I1 要求非负性，就必须测试库存不足的场景；既然 I5 涉及金额差额的归属，就必须测试差额为零的边界。发现一的"零差额"用例正是这样被推导出来的——它是 I5 与 I6 的直接推论。

换句话说，**不变式的完备性决定了边界场景的完备性**。这把测试用例设计的质量从一个经验问题，部分转化为一个逻辑问题。

当然，这一方法也有前提：不变式本身必须正确且完备。若不变式遗漏了某个维度，对应的缺陷仍然无法被发现。本文的七条不变式覆盖了金额与克数两个维度、订单项与批次两个层级，但仍可能存在未覆盖的维度（例如时间维度的最终一致性、跨商户的公平性等）。

### 5.3 效度威胁

本文从四个角度分析结论的效度威胁。

**内部效度（Internal Validity）**。最主要的威胁是**单机单实例环境**。实验在单台机器、单个 MySQL 实例上执行，悲观行锁与条件更新的有效性在此环境下成立，但生产环境通常为多实例部署，此时应用层的锁不再有效（因为锁的作用域是数据库连接而非进程），必须依赖数据库行锁。本文的结论**不应外推到多实例环境**。

其次是**随机序列的覆盖范围**。E1 的 20 轮随机回归无法覆盖所有可能的操作时序，特别是并发时序。本文通过 E3 的固定并发场景部分缓解，但未做并发度扫描。

**构念效度（Construct Validity）**。本文以"不变式成立"代理"一致性正确"，二者并不完全等价。若不变式体系遗漏了某个维度，则不变式全部成立也不意味着系统完全正确。本文在 3.2 节给出了每条不变式的推导依据（而非直接断言），以便读者自行判断其充分性。

另一个构念威胁是**支付渠道的缺失**。系统未接入真实支付渠道，支付成功由人工确认模拟。这可能使支付相关的幂等场景与实际存在差异。本文认为这一威胁有限，理由是支付适配层被设计为可替换边界，一致性机制不依赖渠道实现细节。

**外部效度（External Validity）**。结论依赖 MySQL InnoDB 的行锁语义与唯一约束行为。更换存储引擎（如 PostgreSQL、或在分布式数据库上）可能得到不同结果。此外，本文的订单规模（1–4 个订单项、1–3 个批次）远小于真实电商场景，批次数量与订单复杂度的提升可能暴露新的问题。

**结论效度（Conclusion Validity）**。E2 的对照实验每个场景仅执行一次，未做重复抽样与统计检验。因此本文对"两种粒度在批次级归属上不同"这一结论是**机制性论证**（通过分析实现逻辑与实际观测的一致性）而非**统计性论证**。对于批量化的量化对比，本文留在未来工作中完成。

### 5.4 局限

除上述效度威胁外，本文还有以下明确局限。

1. **未实现大规模组合实验**。原实验设计包含 E2 的 1,080 次组合实验、E4 的并发安全实验（300 次）与 E5 的故障注入实验。受时间限制，本文实际完成的是 E1、E2、E3 三组共 10 项用例，即原设计中的"最小可发表集"。E4 与 E5 未实施。
2. **服务层与持久层缺少单元测试**。现有 42 项测试中，32 项为策略类的纯函数测试，10 项为本文新增的集成实验。中间服务层（编排逻辑）主要依赖端到端测试覆盖，缺少针对性的单元测试。
3. **并发场景样本有限**。E3 的并发实验仅覆盖 10 线程、单一竞争点、单次执行，未做并发度扫描与重复轮次统计，因此无法给出失败率的置信区间。
4. **未度量性能**。本文关注正确性而非吞吐与延迟，未收集任何性能指标。
5. **前置数据由 SQL 构造**。如 4.3 节所述，实验结论限于称重与回补机制，不涵盖下单与支付链路。

## 第六章 结论与展望

### 6.1 结论

本文针对生鲜电商按重量计价所带来的"金额与库存双维度一致性"问题，设计并验证了一套覆盖"预占—核销—回补"全生命周期的一致性机制，主要结论如下。

**第一，形式化不变式可以作为机制设计与验证的共同基础。** 本文提出的七条不变式（I1–I7）覆盖非负性、预占约束、批次守恒、订单项守恒、金额守恒、粒度一致性与分摊无损性，既作为设计约束指导实现，又作为实验判定依据，使结论可被机械验证。在 20 轮固定种子的随机回归中，四条可自动校验的不变式（I1、I2、I6、I7）违反次数为 0。

**第二，分摊算法中的兜底策略使两种粒度的总量误差均为零，但两种粒度的真实差异在批次级归属。** 由于采用"按预占比例计算、最后一批兜底剩余"的策略，即使跨 7 个批次连续取整，回补总量仍精确等于差额，本文原假设中"整单分摊存在可测量误差"的判断被证伪。进一步的对照实验表明，整单模式在多订单项、偏差方向相反且相互抵消时会使所有批次保持不动，从而掩盖批次级的账实偏离；逐项模式则把偏差如实回补到各订单项自身占用的批次。据此本文将核心论点修正为"批次级归属精度比总量守恒更重要"。

**第三，幂等键与唯一约束的组合可保证有效变更次数恒为 1。** 在顺序重放、10 线程并发同键、同实体异键三种场景下，有效变更次数均为 1。三个场景的拦截机制各不相同，印证了单一手段不足以覆盖全部竞态，必须并用。

**第四，以不变式驱动的实验设计具备缺陷发现能力。** 实验过程中发现并修复了一处真实缺陷：结算策略在金额差额为零时仍进入退款分支，导致库存校准操作产生对用户钱包的无谓依赖，并写入 0 元流水。该缺陷并非来自代码审查，而是被不变式体系推导出的边界用例所发现。

### 6.2 未来工作

基于本文的局限，后续工作可从以下方向展开。

**扩展实验规模与维度**。补足原设计中的 E4（并发安全）与 E5（故障注入）实验，并对 E2 做批量化的组合实验与统计检验，以给出误差分布的描述性统计而非单点观测。

**多实例环境下的机制验证**。将系统部署为多实例，检验当前依赖数据库行锁与唯一约束的设计在跨进程竞争下是否依然成立，并评估是否需要引入分布式锁或乐观锁重试机制。

**时间维度的一致性**。本文的不变式刻画的是任意时刻的状态约束，未覆盖"操作最终完成"这一活性（liveness）性质。引入超时释放任务后，需要额外保证"预占记录最终会被核销或释放"。

**批次归属精度的量化度量**。本文以对照实验定性说明了批次归属的差异。未来可定义批次级偏差的量化指标（例如 `Σ_b |账实偏差|`），并在不同订单复杂度下测量其随粒度的变化曲线。

**性能与成本评估**。逐项回补在提升批次精度的同时增加了操作次数，需要评估其在真实分拣吞吐下的成本，以确定粒度选择的适用边界。
